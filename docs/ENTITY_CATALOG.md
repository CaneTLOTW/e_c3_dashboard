# Entity catalog and data quality

## Scope

`e_c3_dashboard` reads Home Assistant entities belonging to the Stellantis vehicle selected during config flow and creates its own package entities under the e-C3 config entry.

It does **not** recreate or rename upstream Stellantis entities. Visible entity IDs are generated by Home Assistant and vary between installations; do not copy examples as fixed IDs.

The current package exposes sensors plus explicit-control `switch`, `button`, `number` and `time` platforms.

## Quality terminology

| Grade | Meaning |
| --- | --- |
| **Diagnostic** | Configuration/compatibility/status information rather than a physical measurement. |
| **Direct / high** | Based primarily on direct upstream state or a valid odometer difference. Still limited by upstream refresh timing. |
| **Derived / medium** | Useful calculated value with meaningful source evidence but dependent on delayed/incomplete upstream data. |
| **Estimated / low** | SOC/time/capacity based approximation. Useful for orientation/trends, not billing or certification. |
| **Control** | Package-owned user action/setting; not a measurement. |

## Package-owned sensors

The sensor platform currently creates the following groups for each config entry.

| Sensor | Purpose | Data-quality notes |
| --- | --- | --- |
| **Dashboard status** | Readiness, selected mapping, module state, package entity mappings, notification/wake-up diagnostics and upstream compatibility. | **Diagnostic.** `ready` means the package mapping is usable; it does not guarantee every optional upstream value or remote channel is currently fresh. |
| **Server trip history** | Canonical Stellantis trip count plus compact history rows/quality fields for the frontend. | Canonical history preserves raw source and can mark/repair derived continuity with provenance. Severe invalid rows do not feed statistics. |
| **Server GPS history** | GeoJSON derived from canonical trip start/stop positions. | Start/stop geometry can be sparse and lines are explicitly approximations, not a complete route trace. |
| **Server charge history** | Canonical/observed charging windows and bounded curve/session attributes. | Observed sessions can contain real package-observed samples; reconstructed windows remain estimates and do not invent unavailable charging telemetry. |
| **Vehicle information** | Backend-supplied brand/motorization/maintenance information for native More Info. | Runtime data can contain vehicle-specific identifiers. Public screenshots/diagnostics must redact them. |
| **Trailing consumption (500 km)** | Consumption over the newest qualifying canonical trips, up to roughly 500 km. | **Derived/estimated.** Distance comes from valid trip distance; energy can be SOC × capacity based. Invalid trips are excluded. |
| **Distance since last charge** | Current odometer minus the reconciled last-charge odometer baseline. | **Direct/high** when a valid baseline and current odometer exist; remains unavailable instead of inventing a baseline when evidence is missing. |
| **Current trip energy** | Live estimated battery-side energy used during an observed trip. | **Estimated/low.** SOC granularity and delayed API updates limit precision. |
| **Last local trip result** | Restart-safe completed locally observed trip result. | Distance can be high quality after delayed odometer arrival; energy/consumption fields remain estimates. |
| **Current charge power** | Battery-side charging-power estimate from recent positive SOC/time samples. | **Estimated/low.** Not charger telemetry; can be sparse or unavailable until a new SOC sample arrives. |
| **Last local charge result** | Completed locally observed charging result with SOC, duration, estimated energy/power and bounded samples. | **Mixed.** Charge type can be upstream/direct; energy and power remain estimates. |

The exact current entity IDs are discoverable from the e-C3 device/entity registry and from the Dashboard status sensor mappings.

## Buttons

The package creates these explicit action buttons:

| Button | Action |
| --- | --- |
| **Wake vehicle now** | Calls the mapped upstream Stellantis wake-up action and records package wake-up diagnostics. |
| **Test notification** | Sends a test only when notification master and at least one explicitly selected/enabled recipient permit it. |
| **Sync server history** | Runs the package's full canonical server-history synchronization. |

A successful button call does not automatically prove the physical vehicle performed the requested action. Upstream command lifecycle and observed vehicle effect remain separate concepts.

## Switches

Base package switches are persisted per config entry and default to **off** on a new installation:

- notification master;
- trip reports;
- charge reports;
- vehicle alerts;
- hourly wake-up;
- wake-up while charging;
- reachability wake-up probe.

For every Notify service explicitly selected in integration options, the package also creates a recipient enable/disable switch. Merely discovering a Notify service does not create consent to send to it.

| --- | ---: | --- |

The notification manager validates related warning/reset semantics so hysteresis is not silently broken by configuration.

## Quiet-hour Time settings

The `time` platform creates:

- quiet-hours start, default `22:00`;
- quiet-hours end, default `07:00`.

These settings control deferred non-urgent availability warnings. They do not globally mute every notification topic.

## Upstream entities used by the dashboard

The dashboard also displays or invokes upstream Stellantis entities such as:

- battery SOC and range;
- mileage/odometer;
- temperature;
- engine and charging state;
- charging type/end time/charge limit where exposed;
- vehicle tracker/current position;
- service battery;
- remote-connection/command status;
- supported upstream remote-action buttons.

Those are **not** package-owned entities. Their semantics, availability and refresh cadence belong to Stellantis Vehicles and the Stellantis service.

The package resolves them from the selected device registry rather than VIN-shaped string construction.

## Canonical trip data quality

A retained raw server row is not automatically treated as trustworthy statistics input.

Canonical processing can evaluate:

- distance;
- duration;
- average speed;
- start/end odometer;
- zero/sentinel odometer values;
- continuity with neighboring valid rows and locally observed evidence.

If a row cannot be supported, it remains invalid and does not become a continuity anchor for following trips. If sufficiently strong evidence supports a narrow continuity repair, only the derived canonical boundary is repaired; raw server fields remain unchanged and repair provenance is retained.

The 0.5.53 accepted repair for the known zero-start case is an example of this behavior.

## Charging data quality

Observed charging sessions can retain timestamped SOC samples in package storage. The frontend receives a bounded compact timeline for display.

When direct charging energy/power is unavailable, the package can derive battery-side estimates from SOC change, capacity and elapsed time. These estimates:

- exclude charger/wallbox losses;
- depend on SOC granularity and update frequency;
- are not suitable for billing;
- should not be interpreted as raw BMS or wallbox telemetry.

## GPS data quality

Home Assistant Recorder tracker history can provide detailed local position points where the upstream tracker actually updated. Canonical server-trip history can add start/stop positions.

The map keeps current position separate from archived history. Straight lines between server start/stop points are approximate geometry, not a claim that the car drove that exact line.

## Home Assistant long-term statistics

The Statistics view may use Home Assistant long-term statistics for mileage/SOH-related sources.

The package does not conceal or directly rewrite malformed existing LTS `sum` history. A confirmed case of repeated statistics-only mileage `sum` resets, with monotonic odometer `state`, is tracked in GitHub Issue #25. That issue is distinct from canonical trip continuity.

## Persistence

Package data is restart-safe and scoped per config entry. It includes separate stores for:

- local metrics/session state;
- canonical server history / retained observed history;
- notification settings/switches/markers/wake-up diagnostics.

Removing or reloading the package must not mutate the selected upstream Stellantis device or rewrite its Recorder history.

## Recorder retention

The configurable **History display window** defaults to 2,160 hours (90 days). It is a query/display window, not a Recorder retention policy.

If Recorder-backed detail is required for the full window:

1. retain the necessary entities for at least that period;
2. include the relevant upstream/package entities if Recorder uses an allowlist;
3. size the database according to the user's own storage/backup policy.

The integration never changes Recorder retention, filters, database backend or purge schedule.

## Explicit non-entities / boundaries

The package deliberately does **not** create household automations, scripts or `input_*` helpers, and it does not store third-party notification credentials or implement a direct Stellantis API client.

Package-owned configuration is expressed through the config/options flow and native e-C3 entity platforms instead of requiring household YAML helpers.
